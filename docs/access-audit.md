# アクセスログと監査

厚生労働省「医療情報システムの安全管理に関するガイドライン」第7.0版 [システム運用編](https://www.mhlw.go.jp/content/10808000/001716295.pdf) §17に対応するための、開発版の監査機能です。

| §17の項目 | RECEPTでの対応 | 導入時の対応 |
| --- | --- | --- |
| ① アクセス記録と定期確認 | APIの要求時刻、操作、結果、患者ID、更新対象IDを記録。サーバーで認証済みの利用者ID・ログイン時刻を受け取るインターフェースを用意 | 個人認証と接続し、定期確認を実施する |
| ② アクセス制限と改変防止 | ログの閲覧・変更用HTTP APIを設けず、ローカルの読み取り専用コマンドで確認する。SQLiteトリガーとハッシュ連鎖を使う | DB・バックアップ・コマンド出力のアクセス権を制限し、チェックポイントを別の保護された保管先に保存する |
| ③ 信頼できる時刻 | サーバー時刻をUTCで記録する | サーバーを組織の信頼できる時刻源と同期し、同期状態を監視する |
| ④ 監査計画と証跡 | 時系列での確認と整合性検証を提供し、記録失敗・アクセス拒否等を監視系に渡せる | 監査担当、頻度、保存期間、異常判定基準、報告先を規程で定め、確認結果と対応記録を残す |

## 記録範囲

- 患者ワークスペースの取得、患者登録・更新、点検補正、デモ会計確定、デモリセット、請求プレビュー・CSV出力要求、確定記録のJSON出力要求、JSONスナップショット要求を記録します。現在の画面は患者一覧を一括で取得するため、その応答に含まれる全患者の内部IDと、操作で変更された患者IDを区別して保存します。画面内での選択や取得済みデータの閲覧、端末側でのファイル保存の成否は観測できません。
- 公式マスターの参照・取込、拒否・入力不備・処理失敗も記録します。氏名、傷病名、摘要、検索文字列、リクエスト本文や認証情報は監査ログに複製しません。内部患者IDを含むログは、患者情報と照合できる機微な情報として扱います。
- 成功イベントはデータの変更と同じトランザクションで確定します。患者情報の取得や出力も、記録後に応答します。監査ログを書き込めない場合、業務の変更はロールバックし、患者情報を返しません。失敗応答を記録できない場合は標準エラーへ通知します。
- 既存DBは初回のAPI利用時にスキーマ3へ移行します。従来の「操作履歴」はデモ画面用に保持します。従来の履歴を監査ログへ移し替えず、デモリセットでも監査ログは消去しません。
- 現行のデモサーバーには個人認証がないため、操作者は `anonymous` と記録します。ログイン時刻・個人別追跡を満たすには、後続の認証機能から検証済みセッションの利用者IDとログイン時刻をサーバー側で渡す必要があります。ブラウザが送る利用者IDや認証情報の値を監査証跡として直接採用しません。

## 確認手順

```sh
npm run --silent audit -- verify
npm run --silent audit -- review 0 100
```

`RECEPT_DB` で参照先を指定できます。監査担当の承認を受け、DBを管理する運用アカウントで実行します。POSIX環境ではDBとディレクトリを所有するアカウントを使用します。DBファイルを読む権限には患者情報の読み取りも含まれるため、監査担当者に業務DBを直接公開できない運用では、運用アカウントが承認済みの監査出力を渡します。

`review` は指定した連番の次から、古い順にJSON Lines形式で返します。次のページは直前に確認した最後の連番を指定します。出力・作業記録は承認された場所に保管し、未承認の共有先には転送しません。

`verify` は記録の連続性とハッシュ連鎖を検証し、成功時に最新の `連番:ハッシュ` を出力します。この値をDBとは別の改変防止された場所に保存し、次回は `npm run --silent audit -- verify <保存した連番:ハッシュ>` で照合します。保存済みチェックポイント以前の削除・書換えも検出できます。SQLiteを直接書き換えられる権限に対しては、独立したチェックポイントやDBへの書き込み権限の制限が必要です。

標準エラーのJSONイベント `access-audit-unavailable` はログの永続化失敗、`access-audit-request-failed` はHTTP 401・403・5xxを示します。院内の監視に接続し、永続化失敗は即時に、拒否や障害の多発は院内で定めた閾値で通知します。定期レビューでは監査担当者が大量の参照・出力、拒否の集中、検証エラーを確認し、調査結果を安全管理責任者へ報告します。
